# BUG-2026-08-25T083007: file-info navigation and long-title display

## Problem

The mpg123 File Info dialog consumes cursor-navigation key events, so the
insertion cursor in editable fields does not move with the arrow keys.  The
dialog also presents ID3v1 title data, which is limited to 30 bytes, while the
playlist can use the full ID3v2 title.  This makes long titles appear
truncated or inconsistent.

## Root Cause Analysis

1. `file_info_box_keypress_cb` is connected to GTK's `key_press_event` but is
   declared `void`; GTK requires a `gboolean` return that says whether the
   event was handled.  The invalid callback result may consume arrow keys
   before GTK's default focused-widget handling.
2. The dialog creates the title entry with a 30-character maximum and loads
   only the trailing ID3v1 tag.
3. The ID3 reader decodes every ID3v2.4 frame size as an ID3v2.3 big-endian
   integer. ID3v2.4 instead uses four syncsafe bytes. A valid frame of 128
   bytes or more therefore moves the parser to the wrong offset and can make
   it reject the whole tag. Both File Info and the playlist then fall back to
   the 30-byte ID3v1 title even though `TIT2` is valid.
4. The bundled general-purpose ID3 writer cannot safely be adopted for this
   fix: it does not preserve unknown frames and can require rewriting the
   audio file when the tag grows. Using it would risk metadata or audio loss.

## Sample-File Investigation

The user supplied `Pierreified - Hertz - Electronic Fridays 2026.7.mp3` has
both tags:

- ID3v2.4 `TIT2`: `Hertz - Electronic Fridays 2026.7` (33 bytes)
- trailing ID3v1 title: `Hertz - Electronic Fridays 202` (30 bytes)
- ID3v2.4 comment: `https://www.youtube.com/watch?v=5fCY72i7EFY`
- trailing ID3v1 comment: `https://www.youtube.com/watch?` (30 bytes)

VLC correctly uses the ID3v2.4 metadata. The tag also contains two large
`TXXX` frames of 1,759 and 1,756 bytes. Their ID3v2.4 syncsafe size fields were
misread as 3,423 and 3,420-byte ID3v2.3 sizes, which made XMMS reject the valid
ID3v2 tag and fall back to the truncated ID3v1 title. The corrected reader now
returns `Hertz - Electronic Fridays 2026.7` directly from this unchanged file.

The focused ID3v2.4 title writer preserves all existing frames (including the
large descriptions, links, and unknown frames) by copying all non-`TIT2` bytes
unchanged. It safely grows the tag through an atomic same-directory rewrite.

## Approved ID3v2.4 Title-Write Plan

1. Add a focused ID3v2.4 title-rewrite module. It will retain every byte of
   all non-`TIT2` frames, padding, and audio; replace or add only one UTF-8
   `TIT2` frame; and reject unsupported tag features (extended headers,
   unsynchronisation, and invalid frame layouts) without changing the file.
2. Rewrite the file through a same-directory temporary file, `fsync` it, and
   atomically rename it only after the new tag and all original audio bytes
   have been copied successfully. Preserve the original file mode. Do not use
   the incomplete bundled ID3 writer.
3. Route Save for enabled ID3v2.4 files through that writer. Retain the legacy
   ID3v1 Save path for files without ID3v2; leave the trailing ID3v1 fallback
   unchanged for ID3v2.4 files because it cannot represent the full title.
4. Add source-slice tests that use an ID3v2.4 fixture containing opaque long
   `TXXX` frames and audio bytes. Verify that a longer replacement title is
   readable after saving, opaque frames and audio are byte-identical, and an
   unsupported tag fails without modifying the fixture.
5. Update manual text and run focused tests, preflight, and distcheck.

## Resolution

XMMS now propagates entry navigation keys, reads standard ID3v2.4 syncsafe
frame sizes, displays the full `TIT2` value, and can atomically replace that
title without altering unrelated metadata or audio. The user confirmed the
original sample file now appears correctly in the playlist without editing.

## Code Audit

The key handler now follows GTK's handled-event convention. ID3v2.4 frame
sizes are decoded according to the syncsafe format, so valid tags with large
opaque frames are no longer rejected in favor of ID3v1. ID3v2 reads and writes
obey the existing Disable ID3V2 preference. The focused title writer preserves
all non-title tag and audio bytes, while unsupported layouts are rejected
before the original file is changed.
