# BUG-2026-08-25T100657: File Info rejects safe ID3v2.3 title edits

## Problem

Saving a title from File Info reports `Unsupported ID3v2 tag; the file was not
changed.` for a valid ID3v2.3 MP3. The dialog can read the title, but the
focused title writer introduced for long-title safety accepts only ID3v2.4.

Reported screenshot:
`/home/tuunanet/Pictures/Screenshots/Screenshot_20260825_100657.png`

Reproduction file:
`~/Music/Pierrefied/Electronic Fridays/Hertz - Electronic Fridays 2025.20.mp3`

The failed Save did not modify the file. `ffprobe` still reports the original
full title `Hertz - Electronic Fridays 2025.20`.

**Security impact: NONE.** The current behavior rejects the write safely. The
follow-up must retain that fail-closed behavior for layouts it cannot preserve.

## Root Cause Analysis

1. The file starts with an ID3v2.3.0 tag and also has a trailing ID3v1 tag.
2. `mpg123_id3v24_write_title()` explicitly requires major version 4, so it
   rejects version 3 before examining its otherwise supported layout.
3. ID3v2.3 and ID3v2.4 use different frame-size encodings: v2.3 uses a
   big-endian 32-bit frame size, while v2.4 uses four syncsafe bytes.
4. ID3v2.3 does not define the UTF-8 text encoding used by the current v2.4
   `TIT2` writer. A portable replacement title must be emitted as UTF-16 with
   a byte-order mark.
5. The sample has no tag flags, extended header, frame flags, or other unsafe
   feature. It contains ordinary frames, including a 877,723-byte `APIC`, two
   large `TXXX` frames, ten padding bytes, and audio beginning immediately
   after the tag. All non-`TIT2` bytes can be preserved verbatim.
6. The historical `ID3_SET_SIZE28` macro shifted output bytes by 27, 18, and 9
   bits rather than 21, 14, and 7. Rewritten tags larger than 127 bytes could
   therefore advertise a truncated tag length even when their frame data was
   otherwise valid. The real-file-sized regression exposed this latent bug.

**Risk level: Medium.** Updating metadata rewrites a 120 MB file. The operation
must remain atomic and must not reinterpret or discard its cover art, long text
frames, padding, trailing ID3v1 tag, or audio.

## Implementation

The version-neutral `id3v2-write` module now supports unflagged ID3v2.3 and
ID3v2.4 tags. It uses big-endian frame sizes and BOM-marked UTF-16 for v2.3,
and syncsafe frame sizes with UTF-8 for v2.4. Unsupported tag features and
flagged title frames still fail before a temporary output file is created.
The shared syncsafe-size encoder now emits the standard 21/14/7/0-bit layout.

## Resolution

XMMS now saves titles in safe ID3v2.3 and ID3v2.4 tags while preserving all
unrelated tag and audio bytes. The supplied ID3v2.3 file was verified through
File Info by the user without the unsupported-tag error.

## Code Audit

The writer remains fail-closed for ID3v2.2, nonzero v2.3 tag flags, v2.4 flags
other than a footer, invalid syncsafe lengths, malformed frame boundaries, and
flagged `TIT2` frames. The replacement is created beside the source, flushed,
closed, and atomically renamed only after all copies succeed. The supplied MP3
was never opened for writing during verification.
